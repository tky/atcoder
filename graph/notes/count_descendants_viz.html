部分木を「区間」に変える
ABC202 E Count Descendants の仕掛け

クエリ (U, D) = 「U の部分木にいる、深さちょうど D の頂点数」。鍵は、頂点に番号を振り直すと部分木が連続区間になること。題材は入力例1(以下すべて1-indexed)。

0. 何に困っていたか

「u は U の部分木にいるか?」を頂点番号のまま考えると、2 の部分木は {2, 4, 5, 6, 7} — 飛び飛びの集合で、所属判定は木を歩くしかない(クエリごとに O(N))。これを「数の比較1回」に変えたい、というのが出発点。

1. スタック走査で番号を振り直す(ステップ実行)

いつものスタック走査で、pop された順に 0, 1, 2, … と番号(=行きがけ番号)を配ります。2 の部分木(オレンジの頂点)の番号がどう並ぶかに注目してください。

スタック(右が上):

最後まで進めると、オレンジの頂点(2 の部分木)の青番号が 2, 3, 4, 5, 6 — 連続になっているのが見えます。理由はスタックの LIFO: 2 を pop した瞬間、2 の子たちは待っていた兄弟(下の方)より上に積まれるので、2 の子孫が尽きるまで兄弟に手が届きません。「部分木を描き切ってから隣へ」をスタックが勝手に保証しています。

2. 2冊の辞書 — order と ins

この番号付けで生まれる対応は双方向で、実装では辞書(配列)が2冊できます。今日いちばん事故が起きた場所です。

添字値答える質問使い道
order[i]順番 i頂点「i 番目に pop されたのは誰?」逆読み納品・行きがけ順のループ
ins[v]頂点 v順番「頂点 v は何番目?」区間の端 ins[U]・リストに積む値
i(順番)0123456
order[i](頂点)1327546
事故の型: 2冊は中身がどちらも usize なので、取り違えてもコンパイラは黙っている。「ins を回して値を頂点扱い」「order のつもりで ins を引く」— どちらも今日実際に踏んだ。迷ったら宣言行の「添字は何? 値は何?」コメントに戻る。

3. 部分木 = 連続区間 [ins[v], ins[v]+size[v])

番号の世界を数直線にすると、各頂点の部分木はこうなります(マスの中は 行きがけ番号、下の小さい字が頂点):

区間同士は「丸ごと包含」か「無縁」のどちらかで、半端に重ならない — 木の入れ子がそのまま区間の入れ子に写る。始点は ins[v]、幅は size[v](典型90-039 の部分木サイズ)。

by_depth を行きがけ順に積む(= order を回す)と、各リストには番号が増える順に入る = ソート済みが無料。頂点番号順に回すとここが崩れる(深さ2を頂点番号順に積むと [5, 4, 3] — 降順)でした。

4. クエリを目で見る

クエリ (U, D) = 「U の区間の中にある、深さ D のリストの番号は何個?」。入力例1の4クエリで確かめてください。

クエリのボタンを押してください。

5. 全体の組み立てとコードの対応

前計算(全部 O(N))
① スタック走査1回で order / ins / depth を同時に作る
② order の逆読みで sizes を納品(典型90-039 そのまま)
③ order を回して by_depth[depth[v]].push(ins[v]) — ソート済みが無料

各クエリ O(log N)
④ d が範囲外なら 0(continue を忘れると二重 push + パニック)
⑤ lo = ins[u], hi = lo + sizes[u] — 区間はいつも半開 [lo, hi)
⑥ 個数 = pp(|&x| x < hi) − pp(|&x| x < lo) — 「未満」2本の引き算(partition_point の約束: 述語は先頭側 true・後ろ側 false)

合計 O(N + Q log N)。新しい道具は「行きがけ順の区間化」1個だけで、残りはスタック走査(DFS編)+ size の納品(039)+ 二分探索(binary_search編)の持ち寄りでした。
